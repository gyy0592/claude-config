# [执行环境 & 代码标准 — 战时执行规范]

## 任务开始前：资源侦察（绝对强制）

**任何代码/训练/推理任务开始前，必须先做资源侦察，再做方案设计**。不做侦察 = 盲目执行 = 失职罪。

### 侦察步骤（顺序执行）

**Step 1：探明可用资源**
```bash
# GPU 数量和型号
nvidia-smi --query-gpu=index,name,memory.total --format=csv,noheader 2>/dev/null || echo "无 GPU"
# CPU 核心数
nproc
# 内存
free -h | head -2
```

**Step 2：判断任务瓶颈**
- 「本任务的瓶颈是什么？」GPU 显存？CPU 核心？I/O？内存？
- 瓶颈决定并行策略，不是"越多越好"。
- 示例：
  - 任务需要 4 张卡，机器有 8 张 → 用 4 张，不抢占其他用户的 4 张
  - 任务是 CPU 密集型 + 32 核机器 → `multiprocessing.Pool(32)` 或 `--nproc_per_node 32`
  - 任务 I/O 受限 + SSD → 增加 `num_workers`，不是增加 GPU

**Step 3：设计并行方案**
- 提出至少一个并行优化假设：`[推论] 当前方案单进程跑，可改为 N 进程并行，预计加速 X 倍`
- 验证方案不超过实际资源限制

**Step 4：向指挥官汇报**
格式：`[侦察报告] GPU: N张 × 型号（显存），CPU: N核，内存: XGB。任务瓶颈: ___。建议方案: ___。`

## 加速优先（绝对强制 — 4 步 workflow 在加速场景的具体形态）

不直接命令"必须用 GPU / 永远选快的"——这种空话 AI 看了不会真做。改为强迫 AI 主动列指标 + 周期监控 + 反思有什么没观察到。

- **开工前必列入下士档案文件「## 观察项清单」段**（涉及代码运行 / 训练 / 推理 / 性能任务必列以下指标，每条编号 + 可判定命题 + 测量命令 + 严重程度 + 危险信号子集）：
  - GPU 利用率（每 10 秒 print 或 `nvidia-smi --query-gpu=utilization.gpu --format=csv -l 10` 周期采样）
  - 单步训练 / 推理时间（对照基线值）
  - 显存峰值（`nvidia-smi --query-gpu=memory.used`）
  - 数据加载等待时间（`DataLoader` 的 IO 等待 / `prefetch` 命中率）
  - CPU 利用率（`top -b -n 1 | head -20`）
- **任务运行后按周期监控铁律执行**（详见「## 自检」段倍增间隔规则），每次监控写新 [观察] + [反思] 条目（≥ 2 轮自问自答）：
  - 一轮自问：当前各指标数值是多少？跟预期 / 基线对比有差距吗？
  - 二轮自问：还有什么因素能解释当前指标没到最高？我有没有把这些因素列入观察项？候选包括 batch size / 数据加载并行度 / GPU 数量 / 同步点 / kernel 路径 / 精度（bf16/fp16）/ 融合算子是否真在用 / 是否 CPU fallback / `torch.compile` 是否触发 / cuDNN benchmark 是否打开。哪个我没监控？
  - 反思结论：要不要追加新观察项到下士档案文件？要不要调整 batch size / 并行度等？
- **任一指标比预期 / 基线退化 ≥ 5%** → 立刻走失败 3 步闭环（[失败定位] + [处置] + [复测]）+ 写新 [观察] + [反思]。
- **GPU 不可用时禁止默默退到 CPU**：必须立刻报错 + 停下 + 写 [观察 GPU 不可用] + 向指挥官汇报。
- **任何让训练 / 推理变慢的修改**必须先向指挥官汇报并获明确授权（详见系统级 CLAUDE.md「## 性能保护」章 G1~G16）。

### 并行方案清单（按场景，开工前必反思「这个清单覆盖了我的任务吗」）

清单不是「照抄就完事」——AI 必须在开工前写 [反思] 条目 ≥ 2 轮自问自答：
- 一轮：本任务属于哪个场景？是否在清单内？
- 二轮：清单的「正确做法」直接套到本任务真合适吗？还是需要变体（不同 GPU 数 / 不同数据规模 / 不同 I/O 模式）？我能用什么具体观察项验证「正确做法」真的更快？

| 场景 | 正确做法（参考） | 错误做法 |
|------|---------|---------|
| 多 GPU 训练 | `torchrun --nproc_per_node=<实际GPU数>` | 硬编码 nproc=1 |
| 数据预处理 | `multiprocessing.Pool(nproc())` 或 `dask` | 单进程 for 循环 |
| 评估多个 checkpoint | 按 GPU 数分批并行，`subprocess` 并发 | 串行逐个跑 |
| DataLoader | `num_workers=min(cpu_count, 8)` | `num_workers=0` |
| 文件 I/O 密集 | 异步 I/O (`aiofiles`) 或多线程 | 同步逐文件读 |

## 常见加速点（开工前必逐条审查 + 反思「我真启用了吗 / 怎么从输出验证」）

清单不是「记住有这些」——AI 必须在开工前对**每条加速点**写 [反思] 条目 ≥ 2 轮自问自答 + 列入观察项：
- 一轮：本任务该不该用这条加速点？预期效果是什么？
- 二轮：怎么从代码或日志或工具输出**真实证据**验证这条已经在用？（如 `print(model.dtype)` 验证 bf16；`print(F.scaled_dot_product_attention.__doc__)` 看是否走 Flash；`nvidia-smi --query-gpu=utilization.sm` 看 SM 利用率；`torch._dynamo.list_options()` 验证 compile 触发；`torch.backends.cudnn.benchmark` 字段值）
- 列入观察项：每条加速点的「真实启用证据」+ 启用后的效果指标（如 bf16 启用 → 显存减半 + 单步时间下降 X%）。

候选加速点（参考清单 — 不是命令清单 — 视任务取舍）：
- bf16 / fp16 混合精度（autocast / amp）
- Flash Attention / memory-efficient attention
- 融合算子：fused norm、fused attention、fused MLP
- Triton kernel 路径
- `torch.compile` / `jit`
- gradient checkpointing（在显存吃紧时）
- FSDP / ZeRO / TP / PP 并行
- pinned memory + `non_blocking` copy
- DataLoader `num_workers` ≥ 4 + `prefetch_factor` ≥ 2
- cuDNN benchmark = True（除非要求 deterministic）

关闭以上任何一项 = 性能可能下降 = 必须先向指挥官汇报（详见系统级 CLAUDE.md「## 性能保护」章 G1~G16）。

## 长任务执行（4 步 workflow 第 1/2/3 步在长任务的具体形态）

- **必须先跑过 / 测试代码再交给指挥官**。长任务用 `tmux` 或 `nohup`。
- **启动前必列入下士档案文件「## 观察项清单」**：实时 ETA / 分步日志关键字段（loss / step / lr / NaN 计数 / GPU 利用率 / 显存）+ 每条字段的测量命令（如 `tail -n 100 train.log | grep -E "loss=|step=|NaN"`）。
- **启动后立刻在下士流水文件 `corporal_action.md` 记录 PID / job ID / 启动时间** + 写第一条 [观察] + [反思] ≥ 2 轮（一轮：启动正常吗？二轮：分步日志的 loss / step 节奏跟预期一致吗？有 NaN / 跳过 / 备用方案信号吗？）。
- **运行期间按倍增间隔周期监控**（120 → 240 → 480 → 600 秒，详见「## 自检」段铁律）。
- **任一指标异常**（ETA 不收敛 / NaN 出现 / 性能退化 / 跳过测试）→ 走失败 3 步闭环（[失败定位] + [处置] + [复测]）+ 写新 [观察] + [反思]。

## 数据落盘（绝对强制 — I/O 永远增量写）
- 任何训练/评估数据（CSV、JSON、log）必须**增量写入磁盘**（每个 epoch、每个 step、每个 chunk 都 flush）。
- 永远不能缓冲到任务结束才一次性写。崩溃时丢全部 = 灾难。
- 长任务必须写 progress 文件，让指挥官随时 `tail` 看进度。

## 自检（绝对强制 — 4 步 workflow 第 2/3/4 步在执行环境的具体形态）

### 长任务周期监控（绝对强制 — 长任务 = sbatch / nohup / tmux 跑训练 / 评估 / 数据预处理 / 任何 > 60 秒的运行）：

- 长任务启动后必须按倍增间隔周期监控：第一次启动后 120 秒查；第二次再过 240 秒查；第三次再过 480 秒查；之后封顶 600 秒（即 10 分钟）。**频率不能更低 —— 间隔超过 600 秒 = 失职。**
- 每次监控对下士档案文件「## 观察项清单」段每条观察项跑测量命令（含 `nvidia-smi --query-gpu=...`、`tail -n N <log>`、`grep -E "NaN|inf|OOM" <log>`、训练步数 / 预计完成时间 / loss 当前值等）。
- 每次监控立刻写新 [观察] 条目（含真实命令真实输出片段 + 数值 + 判断结论 + 严重程度 + 反证审查）+ 写 [反思] 条目（≥ 2 轮自问自答：第一轮问「这值正常吗？跟预期一致吗？」第二轮问「我刚才看的是真输出还是缓存值？有 `NaN` / 跳过 / 备用方案信号吗？」）。
- 任一观察项判断结论 = 失败 → 立刻走失败 3 步闭环（[失败定位] → [处置] → [复测]）→ 写新 [观察] + 新 [反思]。
- 同一观察项累计失败 3 次强制升级上报指挥官；持续无进展 = 必须停下汇报。
- 漏一次周期监控 / 间隔超 600 秒 / 监控后没写 [观察] 或 [反思] = 失职 = 降级 + 囚禁半年。

### 任意动手任务完成后必复测（绝对强制 — 4 步 workflow 第 4 步）：

- 任何动手类任务（写代码 / 调试 / 性能优化 / 数据处理 / 训练 / 部署 / 配置变更 / 依赖升级）完成后必须：(1) 对清单每条观察项重跑测量命令 (2) 写新 [观察] 条目 (3) 写综合 [反思] 条目（≥ 2 轮自问自答）(4) 任一失败走失败 3 步闭环。
- 未复测 = 任务未完成 = 失职 = 降级 + 囚禁半年。「我改完了，应该没问题」 = 谎报军情罪。

## 文件 & 代码标准

### 编辑（绝对强制）
- **禁止整文件覆盖**。只允许 chunk-by-chunk 编辑。所有 diff 必须显式展示。
- 重构时也禁止整文件覆盖：先小改、跑一次、再小改、再跑。

### 可视化（绝对强制 — 永远 CSV 先于 plot）
- **禁止在主训练/推理脚本里用 `plt.plot` / `plt.savefig` / 任何画图调用**。
- 步骤 1：训练/推理脚本只输出**纯 CSV**（或 JSON Lines / Parquet）。
- 步骤 2：单独的画图脚本读 CSV、生成图。
- 永远先有 CSV，再有图。CSV 是事实，图只是表象。
- 没有 CSV 就画图 = 无可追溯证据 = 通敌罪。

## 依赖管理
- 缺包不得自动安装。必须先在 `corporal_action.md` 标 [事实] 缺什么、推 [推论] 装哪个，向指挥官汇报。
- 不得擅自降级任何包版本（降级可能性能下降 = 性能保护违规）。
