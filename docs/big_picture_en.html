Barry's Workflow

Turning an AI coding agent from a “stimulus-response machine” into a “self-reflecting state machine”.
Counter training-set bias, stop the “feels-done” delusion, and let documentation self-evolve.

state machine clean-context rebuttal self-evolving docs anti entropy collapse
Motivation

The problem isn’t compute — it’s that AI never enters a “thinking” state

Modern LLMs have a stubborn failure mode when handling coding tasks: they skip directly from “task received” to “I’m done”, omitting every verification step in between. This isn’t a bug in a particular model, nor a prompt-quality problem — it is a behavioral bias baked in by training data.

USER:
“The code runs slow, speed it up”
VANILLA AI:
Immediately bumps batch_size and calls it done.
Skipped: measuring baseline, profiling for the bottleneck, checking GPU util, considering IO/CPU bottlenecks, changing one variable at a time.
USER:
“Script throws a KeyError, fix it”
VANILLA AI:
Wraps it in try/except and moves on.
Skipped: finding out why the key is missing, checking whether upstream forgot to write it, addressing the root cause rather than the symptom, adding a regression test.
USER:
“Build an HTML visualization”
VANILLA AI:
Writes the code, commits, reports “done”.
Skipped: opening in a browser, clicking through interactions, checking console errors. This actually happened during development of this workflow — a quote bug silently killed the entire JS block and the AI never noticed.

Why does this happen? Because the text format of GitHub commits / StackOverflow / blog tutorials is problem → fix — a single hop. The intermediate steps simply don’t appear in training data:

  • Nobody writes “I read 200 lines of code before changing this one line” in a commit message.
  • SO answerers don’t include “I reproduced it 5 times before drawing a conclusion.”
  • “Added tests to verify no regression” — that kind of homework doesn’t attract upvotes, so nobody writes it.

What AI learned is the problem → answer mapping — without the process in between. To get AI to reliably solve complex problems, the intermediate steps must be enforced from the outside.

Phenomenon

Entropy Collapse — open 10 AI instances and they all walk the same wrong path

This is the most counterintuitive yet most critical fact about LLM workflows: N independent AI copies facing the same problem fail in highly similar ways — because they share the same training distribution. The naive idea of “spin up more AIs to review each other” doesn’t work; they all make the same mistakes together.

Training-set bias → shared failure modes → naive multi-copy review doesn’t help

This is the second core motivation of this workflow. To break entropy collapse, different AI instances must be placed in different information states:

  • The main AI has walked a path, made commitments, and tends to prove itself right.
  • A clean-context AI is dispatched to review — it has no “I’m almost done” bias.
  • The two sides argue, forcing the main AI to confront blind spots it missed.

In this workflow that mechanism is called “clean-context rebuttal”. More on that below.

Solution

Two core principles

AI is conditional generation. The output distribution is shaped entirely by what we feed in — prompt, context, files. “State” is just a name for the set of active conditions. Controlling state = controlling conditions = steering the distribution toward the outputs we actually need.

This workflow provides two types of conditions, both required: the designed workflow (condition source A) gives the AI the right structure; the self-evolving docs (condition source B) give it the right priors for this project. Both are conditions. Both are necessary.

Principle 1

State-machine view

Treat the AI as a finite state machine. Its default transition is a single hop: task received → I’m done.

Our job is to cut that single edge into multiple states that must be traversed explicitly, each one forcing the AI to do something specific:

  • BOOT — read existing materials, learn the project history
  • PREPARE — list known facts, define success criteria
  • REFLECT — dispatch a clean-context AI to push back once
  • EXECUTE — write intent + verification evidence for every step
  • REFLECT post — verify the deliverable, add tests

Transitions between states are enforced by the system; the AI cannot skip.

Principle 2

Self-evolving docs

Counter entropy collapse: let accumulated documentation push the AI away from training-set defaults. Each project continuously records:

  • bitter_lessons.md — pitfalls hit in this project (e.g. bs=32 always OOMs on H100)
  • successful_fixes.md — what actually worked in this project
  • rule_violations.md — behavioral mistakes the AI made in this project
  • goal.md — the user-written project goal

There are also global docs across projects capturing wisdom like “this user prefers minimal edits / prefers English replies / rebuttal at 12 min is too heavy for small tasks”.

The AI reads relevant docs at the start of each state; accumulated project knowledge overrides model defaults.

Mechanism

Clean-Context Rebuttal — countering the “feels-done” delusion

This is the most important state in the state machine (REFLECT). It directly addresses entropy collapse and confirmation bias.

How it works

1️⃣ The main AI writes its current plan / what it has done / the conclusions it reached into a markdown file.

2️⃣ A clean-context copy is launched — it has not seen the conversation history and carries no “I’m almost finished” commitment.

3️⃣ The copy reads the markdown and independently validates: are there gaps in the plan? Is the observational evidence sufficient? Are there alternative root causes?

4️⃣ The main AI reads the review and may push back once. The two sides go back and forth until they reach consensus or the round limit is hit.

5️⃣ Consensus = the main AI has genuinely considered the objections — not just “I think it’s right so it is.”

The core value of this mechanism: the main AI and the copy are in different information states (one has commitment, the other doesn’t), so they will not simultaneously miss the same thing.

Measured in production during this workflow’s development: one rebuttal round ≈ 12 min / 60k tokens. Worth it for design decisions, complex plans, and bug-hunts; not worth it for small changes. So the state machine selectively triggers this based on scenario.

Architecture

Universal state machine + scenario patches

In practice, “doing a task” comes in many flavors — long monitoring jobs, bug fixes, perf tuning, new features, research. A single set of state machine parameters cannot be optimal for every scenario. So the design is two-layered.

Patch examples

long_monitor.md
Long-running monitoring jobs. Overrides the default cadence — uses T_queue / 5 for queue polling, T_run / 20 for initial dense monitoring, then backs off to T_run / 5 after 2 consecutive clean polls.
bug_debug.md
Known error. Forces reproduce-before-fix; 3 failures trigger REFLECT on-anomaly with 2 rebuttal rounds.
perf_debug.md
Performance optimization. Must measure baseline numbers first, change one variable at a time, and read steady-state utilization — not warmup.
exploration.md
Open-ended research with no clear solution upfront. Pre-task REFLECT enforces 2 rebuttal rounds (key assumptions must have been challenged).
simple-fast.md
Trivial tasks like fixing a typo or adding a print. Skips the heavyweight REFLECT, but post-task verification is retained.

Self-evolution loop — how condition source B narrows the distribution

Patches have two sources — each is a pathway for injecting new conditions into future sessions:

  • Manual — the user sees the AI fail in a scenario and writes a patch to correct it.
  • AI-generated — session hits a pitfall → AI records it in bitter_lessons.md → recurring pattern gets drafted into a patch → user reviews and promotes to active → permanently injected as a condition going forward.

The longer it runs, the more conditions accumulate, and the AI’s output distribution in this environment diverges further from vanilla training-set defaults — getting more accurate on this project the longer it runs. Entropy collapse is partly a self-evolution failure: without accumulated project-specific knowledge, every session starts from the same distribution and makes the same mistakes.

Recap

Three sentences

  1. The problem: AI never enters a “thinking” state — it skip-to-done past intermediate verification, and multi-copy entropy collapse makes naive peer review useless.
  2. The method: a state machine forces the AI through required intermediate steps; clean-context rebuttal breaks confirmation bias; self-evolving docs counter training-set bias.
  3. The value: the AI gets more accurate on a project the longer it runs, instead of repeating the same elementary mistakes every session.
