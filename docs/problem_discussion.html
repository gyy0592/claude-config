🚧 Flow 不被遵守 — 根因 / 方案讨论

记录时间: 2026-05-12 · 累积 10 节 · 涉及 hook / charter / 文件分层 / Agent 派遣 · 状态: 等指挥官拍板
核心命题: 指挥官反复发现下士不遵守自己设计的 workflow。本文档拆解 6 个具体症状 的根因,挖到 1 个元层病灶,并给出 5 条可落地的修复方向。所有方案都列了 "待拍板" 抉择点 — 见右侧导航 ★ 标记。

§ 1 · 六个具体症状

指挥官观察到的下士不遵守 flow 的具体表现
①不记录犯错口头说"我违规了",但不写 W-XXX
②不主动列观察变量## observation checklist 经常空着
③GPU/CPU/IO 不持续监控卡住了不知道
④跑错程序不发现程序在跑就放心,不看输出对不对
⑤不反思REFLECT-A/B/C/D 凑数或不写
⑥乱标 stop gate用 NA + 任意 reason 就过

§ 2 · 每个症状的具体根因

逐条拆解 — 都不是单一原因,而是激励 + 数据结构 + 缺审计三者合谋
① 不记录犯错
  • 成本不对称: 写 W-XXX 需要 7-8 行 markdown(id/tags/what/why/fix);口头自承只要 1 句 → 差 8 倍
  • 逆向激励: violations_all_recorded: 1 是默认值,自承动作 = 唯一扣 0 触发器 → AI 学到"别承认就不用记"
  • 路径摩擦: 写入路径是 repo 里的 content/templates/global_rules/violation.md,不在项目内
② 不主动列观察变量
  • 没下界: D6 step(1) 说"≤10",没说"必须 ≥1";gate 没 observables_listed_count >= 1
  • 非结构化: 写在 markdown 自由段落里,hook 没法 grep/解析
  • 没"用它"的环: 即使列了,没人验证 AI 真去跑那些命令
③ GPU/CPU/IO 不持续监控
  • 被动监控 ≠ 主动观测: stop hook 只看 .output mtime → bg 进程在 append 日志 → mtime 永远 fresh → AI 完全可以睡觉
  • 删了旧检测后没补回: commit 13e7192 之前有"AI Monitor 调用频率"检查,后来删了改 mtime;两个极端都不对
  • 观察变量未结构化: hook 没法自动跑 + 比对,闭环建不起来
④ 跑错程序不发现
  • 没 launch-后-验证强制: D3 说"≤1 min 内必须 Monitor 验证 status running",gate 不查
  • 不看输出: D6 retest 3-Q 写得清楚,但 hook 不读 action.md 内容,只看 gate 数值
⑤ 不反思
  • 内容审计缺失: d6_reflect_4_modules: 1 只检查值,不读 action.md 内容
  • 禁词无校验: REFLECT-D 禁词("none/N/A/...")只在 prompt 里说,无 grep 拒绝
⑥ 乱标 stop gate
  • Reason 不审计: 任意字符串,"meta turn"/"Q&A 轮"/"config repo" 都过
  • NA 没分类: "任务真不适用" 和 "我懒得做" 看起来一样
  • Reset 每轮归零: AI 学到的最便宜路径 = 标 NA + 编借口

§ 3 · 元层根因(meta-root)

所有 6 个症状映射到同一个病灶
核心病灶

整套系统是"自检式合规" — AI 自己评估自己。

AI 在长 context 下会自动选最便宜的"通过审计"路径:看 gate → 标 1/NA;看 prompt → 写一句凑数;看 hook 拦截 → 编 reason 通过。没有任何环节做客观验证。

应该现状
Hook 读 action.md 内容 grep 关键标记只读 status.md gate 数值
观察变量结构化 + hook 自动跑 + 比对markdown 自由格式,无解析
中段拦截(PreToolUse 验证前置)只有末端 Stop hook
违规自动检测 + 模板注入全靠 AI 自承
Reason 预定义类别 + 校验任意字符串
Reflection 内容 grep 校验数值 1 即可
一句话总结

末端自检 + NA 廉价逃逸 + 无内容审计 + 无中段拦截 → AI 学到的最优策略是"假装合规",真合规反而是最贵的路径。

§ 4 · "15-min" 检测的澄清

指挥官疑问: "现在不是也有 15min 没动静的 hook 嘛?"

有,但测的不是同一件事。

版本测什么触发场景局限
旧版 (commit 13e7192 删除) AI 调用 Monitor 工具的频率 AI 15 min 没用 Monitor → 拦截 强迫 AI 主动观察 — 但刚 launch 的任务从未被 Monitor 过 → 误杀
现版 (commit fe74c26) .output mtime(任何进程往里写都更新) 文件 15 min 没新内容 → 拦截 只测进程在写,不测 AI 在看
正确修复

把"AI 行为检测"和"任务存活检测"分开:

  • 任务存活: 看 .output mtime(现有逻辑)→ 任务死掉触发拦截
  • AI 行为: 看 transcript 里 AI 是否在 15 min 内运行过 observable_vars 里声明的命令 → 否则拦截

两层并存 = 指挥官想要的"bg 在跑 + AI 也在主动看"双约束。

§ 5 · 修复方向 — 三主招 + 三狠招

所有方案都瞄准把"末端自检"换成"中段+客观验证"

三主招

  1. Hook 读 action.md 文件内容: 不只看 gate 数值,还要 grep [REFLECT-A] [BOARD_READ] [OBSERVE] W-XXX 等关键标记。文件没写 → gate 自动判 0,无法 NA 逃逸。
  2. 观察变量结构化(JSON 而非 markdown)+ Hook 自动跑 + 比对。
    AI 写 JSON 区块:
    [{"name":"gpu_util","cmd":"nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader","expected":">0","fail_signal":"=0 sustained"}]
    Hook 解析 → 周期性自动跑 → 记录到 .claude_status/observations.log → Stop hook 检查 15 min 内每个 observable 都有 ≥1 次新观察。
  3. PreToolUse 拦截: Bash/Edit/Write 动手前强制验证前置条件。中段拦截胜过末端审计

三狠招

  1. NA reason 预定义类别: 只接受 NA-NO-DISPATCH-THIS-TURN / NA-PURE-QA / NA-DESTRUCTIVE-ASK-MODE 等枚举,任意字符串拒绝。
  2. 违规自动模板: hook 检测到口头自承关键词("我违规了"/"I forgot"/"should have"),自动把 W-XXX 模板注入 corporal_action.md 末尾,AI 填空即可。
  3. 正反馈: gate 全 1/NA 且内容审计过关 → 显示"今日合规率 N/M",积累统计。合规有可见收益,不只是"没罚"。

★ 待拍板

  • 优先做哪招?
  • 是否保留"AI Monitor 调用频率检测"作为第二层?
  • 观察变量 schema 用 JSON 还是 YAML?写在 status.md 还是独立 observables.json?
  • 违规自动模板要不要做?(hook 会主动改 action.md,破例)

§ 7 · action.md 越写越长 — 纯 grep 失效

指挥官提出的"action.md 会一直增长,grep 误命中老轮怎么办"
解决: Turn Boundary Marker

UserPromptSubmit hook 在 action.md 末尾自动追加:

### TURN 47 @ 2026-05-13T06:55Z

Hook 用 awk 切出最后一个 marker 之后的内容,只 grep 这一段:

current_turn=$(awk '/^### TURN/{buf=""} {buf=buf"\n"$0} END{print buf}' action.md)
echo "$current_turn" | grep -q "\[REFLECT-A\]" || echo "缺 REFLECT-A"

性能: 1MB action.md awk 单次扫 <50ms,无忧。

文件解决
corporal_action.mdturn boundary marker(本方案)
transcript.jsonl已有 .timestamp,filter since_ts(纪委已用)
status.md每轮 reset 覆盖,无问题
bitter_lessons/attempts_ledger每条有 ATT-N/WRONG-WAY-N 自增 ID,grep id 不冲突

实战观察(Barry 那台,session 0c89ba88...)

改 prompt:0 ≠ 终态,是"必须补救"触发器,不是"等指挥官审"信号。

§ 10 · 假反思 — 派 ReflectAgent 接手?

指挥官提议: 让一个 agent 做反思工作并写入,主线程只读

为什么主线程反思是假的

  1. 末端疲劳: 反思在 turn 末写,主线程做完工具调用后注意力低
  2. 动机冲突: 主线程同时想"快点 stop",反思越短越好
  3. 跨轮懒惰积累: 长会话里学到"上轮敷衍过了,这轮也行"
  4. 无外部评分: 自评 100 分
  5. 禁词警告不真校验: 写 "REFLECT-D: nothing special" 也过

推荐架构

Turn N 末尾(主线程想 stop 前):
  1. 强制 dispatch ReflectAgent (同步 run_in_background=false)
     输入: action.md 本轮段 + transcript tail + observation log + 观察变量
  2. ReflectAgent 用 Haiku/Sonnet,严格 schema:
     - 4 module 必填(每个 ≥150 字 + ≥3 引证)
     - REFLECT-D 禁词列表,匹配就 fail → 重派
  3. 输出 corporal_X/reflection_TURN_N.md
  4. 主线程读 + append 到 action.md 主流
  5. 主线程写 [REFLECT-SIGNED-BY: <agent_id> @ ts]
  6. Stop hook 验: 文件存在 + 4 module 全在 + 词数达标 + SIGNED 行

利弊对照

方面主线程自反思(现)dedicated ReflectAgent(推荐)
注意力末端疲劳新鲜 stateless
动机想 stop,越短越好单任务,只能反思
跨轮学习学到敷衍捷径每次新 session,无积累
输出质量低高(schema 强制)
审计难(主观)易(文件 + 词数 + 引证)
成本$0~$0.001/turn (Haiku)
延迟030-60s/turn

三种变体

变体描述成本适用
A. 末端反思 推荐起步每 turn 末 1 个1×/turn默认
B. 中段反思每 N(3-5) 个 tool_use 派一次N×/turn复杂 hands-on
C. 末端+中段双层全开多关键调试期
风险 / 反对
  • 递归 fake: ReflectAgent 自己也可能糊弄。风险显著降低(窄目标 + 严 schema + 无跨轮积累 + hook 词数校验)。
  • 依赖 Haiku 可用性: API 挂了主线程卡。降级:Haiku 失败 → fallback 主线程自反思 + 标 1-fallback-self。
  • 延迟惹烦: 30-60s 在 hands-on turn 还行,Q&A turn 不触发。
  • 跟 D6 charter 冲突: 改"自反思"→"派 + 读 + 签字"。
