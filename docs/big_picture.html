动机 / Motivation

问题不在算力，在 AI 不会进入"思考"状态

现代 LLM 处理 coding 任务时有个很顽固的失败模式：把"接受任务"直接跳到"我做完了"，中间所有验证步骤一概省略。这不是某个模型的 bug，也不是 prompt 不够好的问题，而是训练数据决定的行为偏置。

USER:
"代码跑得慢，加速一下"
VANILLA AI:
直接改 batch_size 一把梭。
跳过了：测 baseline、profile 看瓶颈、看 GPU util、考虑 IO/CPU 瓶颈、一次只改一个变量。
USER:
"脚本报 KeyError，修一下"
VANILLA AI:
用 try/except 包住继续。
跳过了：查 key 为什么不存在、看上游是不是漏写、找 root cause 而不是 symptom、加测试防回归。
USER:
"做一个 HTML 可视化"
VANILLA AI:
写完代码 commit、汇报"完成"。
跳过了：用浏览器打开、点击交互、看 console error。本工作流开发期间真的发生过，引号 bug 导致 JS 整段挂掉，AI 自己没发现。

为什么这样？因为 GitHub commits / StackOverflow / blog 教程的文本格式都是 问题 → 修复 的单跳对，中间步骤训练集里压根不出现：

  • 没人会在 commit 里写"我先 read 了 200 行代码才改这 1 行"
  • SO 答主不会贴"我先复现了 5 次才下结论"
  • "加了测试验证没回归" — 这种功课没法吸引点赞所以没人写

AI 学到的就是 问题 → 答案 这个映射，没学到中间过程。要让 AI 真正解决复杂问题，必须从外部强制把中间步骤补回来。

现象 / Phenomenon

Entropy Collapse — 开 10 个 AI 全走同一条歪路

这是 LLM 工作流最反直觉但最关键的事实：独立的 N 份 AI 副本面对同一个问题，错的方式高度相似。因为他们共享同一个训练分布。"多开几个 AI 互相 review"这种朴素思路不管用 — 大家会一起犯一样的错。

训练集偏置 → 失败模式共享 → 朴素多副本 review 没用

这是本工作流的第二个核心 motivation。要打破 entropy collapse，必须让不同的 AI 实例处于不同的"信息状态"：

  • 主 AI 已经走了一段路、有 commitment、倾向证明自己对
  • 派出一个干净上下文的 AI 来 review — 它没"我已经做完了"的偏见
  • 两边互相反驳，主 AI 被迫面对自己没注意的盲点

本工作流里这个机制叫做"clean-context rebuttal"。后面会讲。

解决方向 / Solution

两个核心原则

AI 是条件生成（conditional generation）模型。输出分布完全由输入决定——prompt、上下文、读入的文件，这些就是「条件」。「状态」不过是当前激活的条件集合的名字。控制状态 = 控制条件 = 把分布收窄到我们需要的输出。

本工作流提供两类条件，缺一不可：设计好的工作流（条件来源 A）给 AI 正确的结构；自我进化文档（条件来源 B）给 AI 对当前项目正确的先验知识。两类都是条件，两类都必须有。

核心 1

状态机视角

把 AI 看成一台 finite state machine。它默认的状态转移是 接受任务 → 我做完了 一跳到底。

我们的工作是把这条单跳边切成必须显式走过的多个 state，每个 state 强制 AI 做特定的事：

  • BOOT — 读已有材料、知道项目历史
  • PREPARE — 列已知信息、明确成功判据
  • REFLECT — 派 clean-context AI 反驳一次
  • EXECUTE — 每步写意图 + 验证证据
  • REFLECT post — 验 deliverable、加测试

state 之间的转换由系统强制，AI 不许跳。

核心 2

文档自我进化

对抗 entropy collapse：让累积的文档把 AI 推离训练集默认轨迹。每个项目持续记录：

  • bitter_lessons.md — 这个项目踩过的坑（bs=32 在 H100 必 OOM）
  • successful_fixes.md — 这个项目成功修法
  • rule_violations.md — AI 在这项目里犯过的行为错误
  • goal.md — user 写的项目目标

跨项目还有全局文档记录"该 user 喜欢最小修改 / 喜欢中文回复 / rebuttal 12 分钟对小任务不值"等行为智慧。

AI 在每个 state 开始时 Read 相关文档，累积的项目知识压过模型默认偏置。

关键机制 / Mechanism

Clean-Context Rebuttal — 反"觉得自己做对了"

这是状态机里最重要的一个 state（REFLECT）。专门解决 entropy collapse 和确认偏差。

怎么工作

1️⃣ 主 AI 把自己当前的 plan / 已经做了什么 / 想得出的结论，写到一个 markdown 文件。

2️⃣ 启动一个干净上下文的副本 AI — 没看过对话历史、没"我快做完了"的 commitment。

3️⃣ 副本读 markdown，独立验证：plan 有没有漏点？观察证据够不够？还有没有替代根因？

4️⃣ 主 AI 看 review，可以反驳一次。两边来回讨论直到达成共识或者轮数上限。

5️⃣ 共识 = 主 AI 真的考虑过反对意见，不是"我觉得对就对"。

这个机制的核心价值：主 AI 跟副本处在不同信息状态（一个有 commitment，一个没有），所以他们不会同时漏掉同一个东西。

本工作流开发期间实测：单次 rebuttal ≈ 12 分钟 / 60k token。对设计决策、复杂 plan、找 bug 划得来；对小修改不值。所以状态机针对不同场景选择性触发。

架构 / Architecture

通用状态机 + 场景补丁

现实里"做任务"分很多种 — 长监控、修代码 bug、性能调优、写新功能、调研。同一套状态机参数不可能对所有场景最优。所以分两层。

补丁示例

long_monitor.md
长跑监控任务。覆盖默认 cadence — 用 T_queue / 5 估队列 poll、T_run / 20 估初始密集监控、连续 2 次干净后切 T_run / 5 疏松。
bug_debug.md
已知错误。强制先复现再改、3 次失败强制进 REFLECT on-anomaly 2 轮 rebuttal。
perf_debug.md
性能优化。必先测 baseline 数字、一次只改一个变量、看稳态利用率而非 warmup。
exploration.md
没明确方案的调研。pre-task REFLECT 强制 2 轮 rebuttal（关键词必须被质疑过）。
simple-fast.md
改 typo / 加 print 这种小任务。跳过大头 REFLECT，但保留 post-task 验证。

自我进化闭环 — 条件来源 B 如何收窄分布

补丁有两个来源——每种来源都是把新的条件注入未来 session 的途径：

  • 人工 — user 看到 AI 在某场景下做砸，写一个补丁修
  • AI 自动 — session 踩坑 → AI 写到 bitter_lessons.md → 反复出现的坑由系统起草补丁草稿 → user 审核升 active → 永久注入为条件

跑得越久，积累的条件越多，AI 在这套环境里的输出分布越来越脱离 vanilla 训练集行为——在这个项目上越用越准。Entropy collapse 的根本原因之一是自我进化失败：没有项目知识积累，每次都从同一个分布出发犯同样的错。

总结 / Recap

三句话

  1. 问题：AI 不会进入"思考"状态，跳过中间验证，多副本 entropy collapse 互相 review 没用。
  2. 方法：状态机强制 AI 走必须的中间步；clean-context rebuttal 打破确认偏差；文档自我进化对抗训练集偏置。
  3. 价值：让 AI 在某个项目上越用越准，不再每次都犯同样的低级错。
