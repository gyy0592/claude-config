## 1. 三项修复

### F1 — viewer 实时刷新

**问题**：viewer 是 `python3 -m http.server` 静态服务，数据通过 `start_viewer.sh` 一次性 `shutil.copy2()` 从 `.barry_workflow/<sid>/` 复制到 `viewer/data/<sid>/`。源更新后副本不变；前端无 polling/WebSocket/SSE。

**根因（来自先前 agent 调查）**：
- 文件系统层：snapshot 复制
- HTTP 层：http.server 无 push
- 前端层：viewer.js 无 setInterval/EventSource/WebSocket
- JS 缓存层：`state.fileCache` 只在切 session 时清

**修复设计**：
1. **数据源 live 化**：`scripts/build_viewer_manifest.py` 把 `state.md` 和 `action.md` 从 `shutil.copy2` 改成 `os.symlink`（force-overwrite 已有目标；symlink 指向源 `.barry_workflow/<sid>/state.md`）。`python3 -m http.server` 默认 follow symlink（CPython `SimpleHTTPRequestHandler` 行为）。**升级兼容**：写 symlink 前若目标存在且**不是 symlink**（即旧 snapshot 真文件），先 `os.remove` 再建——这样老用户 git pull + 重启 viewer 即自动升级，无需手动清理。**`build_viewer_manifest.py` 的幂等 mtime 检查同时绕过**：当目标是 symlink 时 mtime 跟随源，已经 live；当目标是真文件需要被替换时，先 remove 触发 ingest 路径走全程。
2. **派生文件保持 snapshot**：`cleaned_transcript.json`、`agent-*.meta.json` 这些是 `extract_transcript.py` 产物，不在源目录，继续 copy。
3. **前端 polling**：`viewer/viewer.js` 新增 `setInterval` 每 5 秒 re-fetch 当前 sid 的 `state.md` + `action.md`（query string `?t=<epoch>` cache-bust），刷新左栏 + 右栏对应 panel。**只重渲染变化的 panel**，避免滚动跳。
4. **可关闭**：viewer 顶栏加 `[ ] Auto-refresh` checkbox，默认开。localStorage 持久。

**改的文件**：
- `scripts/build_viewer_manifest.py`（symlink 替换 copy2 for state/action）
- `viewer/viewer.js`（setInterval + cache-bust fetch + 增量渲染）
- `viewer/index.html`（auto-refresh checkbox UI）
- `viewer/viewer.css`（checkbox 样式）

**测试**：
- 升级路径测试：先用旧版跑一次（snapshot 真文件），切到新版重启 viewer，确认 `viewer/data/<sid>/state.md` 自动变成 symlink（`ls -la` 看 `->`）。
- 实时刷新测试：本地 `bash scripts/start_viewer.sh`，浏览器打开；另一终端 `echo "test" >> .barry_workflow/<sid>/action.md`；≤ 5 s 内 viewer 右栏 action panel 应出现新行。
- Auto-refresh 关闭测试：勾掉 checkbox，再 append 源文件，viewer 应**不**更新。

**成功标准**：源文件 append 后 5 秒内 viewer 显示更新；切 session 不丢 polling；关 checkbox 后停 polling；浏览器 console 无 error。

### F2 — 全局 ledger 纳入 cache_hit_map

**问题**：router 每轮要求 grep `~/.claude/rules/violation.md` 和 `lessons.md` 的 `tags:`，但 `prepare_helper.sh` 没把这两个文件枚举进 cache_hit_map。模型无从声明它们是否在 KV 缓存。

**注意**：项目层 `workspace/bitter_lessons.md` / `rule_violations.md` 等已经被 `workspace/*.md` glob 覆盖（v2.4_plan 写作此刻在远程 LLM_sampling_thinking 实跑 `prepare_helper.sh` 验证：17 行，4 个共享 ledger 都在）。**老 session 缺这几行**的原因是 PREPARE 时间早于 ledger seed 时间，不是代码 bug。

**修复设计**：
1. `hooks/prepare_helper.sh` 在 artifact 枚举末尾追加：
   ```bash
   for f in "$HOME/.claude/rules/violation.md" "$HOME/.claude/rules/lessons.md"; do
       [ -f "$f" ] && artifacts+=("$f")
   done
   ```
2. 路径在输出 stub 时仍 `${f#${CWD}/}` 处理 —— 但全局路径不在 CWD 下，这段需要分支：CWD-prefix 命中走相对路径，否则 emit 绝对路径（或用 `~/` 缩写以便阅读）。
3. `hooks/session_boot.sh` P17 inherit 的 regex 不用改（按整块 yaml 拷贝，对新 key 透明）。
4. viewer.js `parseState()` 不用改（cache_hit_map 整块 raw 渲染）。

**改的文件**：
- `hooks/prepare_helper.sh`

**测试**：在本地仓库 `bash hooks/prepare_helper.sh`，输出最后两行应是 `~/.claude/rules/violation.md` 和 `~/.claude/rules/lessons.md`（若文件存在）。

**成功标准**：新 session 的 cache_hit_map 包含两个全局 ledger 行；signal `sig:` 字段非空。

### F3 — 200k token 周期性 cache 复核 + ledger 合规自检 banner

**问题**：两条并行的隐疾——
1. cache_hit_map 在 PREPARE 一次性填写，跨 session 通过 P17 inherit 复用。长 session 末尾 KV cache 可能驱逐早期 artifact，但模型仍可能凭旧 YES 跳过 Read。
2. **"记了不用"**：bitter_lessons / rule_violations / global lessons + violation 写了大量 W-XXX / L-XXX，但实际工作时模型若不主动 grep，再多积累也不能进化。BOOT state 虽然要求 grep `tags:`，长 session 中段后基本失效。

200k banner 是周期性"强制召回"机会——既复核 cache，也复核是否在重复犯老错。

**用户原方案**：「比如超过 200k？ 我看你可视化都可以记录对话 token 开销之类的了 就每 200k 做一次输入」

**修复设计**：
1. 新 hook `hooks/cache_refresh_check.sh`：UserPromptSubmit 时触发。
   - 读 `~/.claude/projects/<encoded-cwd>/<sid>.jsonl` 最后一行 `message.usage.input_tokens`（含 cache_read）作为累计输入近似（**注**：jsonl 每行的 `input_tokens` 是该轮的输入，需要累加；或更便宜地用 `cache_read_input_tokens` + `input_tokens` 之和 ÷ 行数估算。先取**累加 input_tokens** 一种实现，简单可靠）。
   - 读 `.barry_workflow/<sid>/cache_refresh.json`（`{last_total: int, last_ts: iso}`）。若无，视为 `last_total=0`。
   - 若 `current_total - last_total >= 200000`：echo 一段 banner 到 stdout（被 Claude Code 拼到 prompt 前），内容为：
     ```
     [CACHE_REFRESH_BANNER · +Δ tokens since last check]
     长会话累计 input_tokens 已超阈值（200k）。请在下一次工具调用前完成 2 项复核：

     A. cache_hit_map 复核
       1. 重读 .barry_workflow/<sid>/state.md 的 cache_hit_map
       2. 对其中 hit: YES 的 artifact，若 ≥ 3 轮未实际访问，把它降为 hit: NO 并本轮 Read 一次

     B. ledger 合规自检（防止"记了不用"）
       1. grep workspace/bitter_lessons.md 当前 task: 同名 + 相关 tags: 行——本轮工作是否在重复已有坑?
       2. grep workspace/rule_violations.md 当前 task: + tags:——本轮是否已经犯过同款 AI 违规?
       3. grep ~/.claude/rules/{lessons,violation}.md tags:——跨项目级别有没有相关条目?

     完成后写一行 [CACHE_REFRESH_DONE 检查项 A+B] 到 action.md
     ```
   - 写回 `cache_refresh.json` 更新 `last_total`。
2. 阈值放 `content/rules/workflow_config.yaml`：`cache_refresh.threshold_input_tokens: 200000`，hook 用现有 `_session_lib.sh::read_config` 读。
3. `set_claude.sh` 注册新 hook 到 `settings.json` 的 `UserPromptSubmit` 列表（与 `session_boot.sh` / `inject_router.sh` 并列）。
4. viewer：在 `state.md` 渲染区下方加一个小角标 "next cache refresh at: <total>+200k = <Δ remaining> tokens"（可选 nice-to-have，不在 must-have）。

**改的文件**：
- `hooks/cache_refresh_check.sh`（新）
- `content/rules/workflow_config.yaml`（加 `cache_refresh` 段）
- `set_claude.sh`（hook 注册段加一行）
- `docs/DEVELOPER.md` §2.10（cache_hit_map 一节追加"周期性刷新"）
- 可选：`viewer/viewer.js`（角标）

**测试**：
- 单元测试：手写一个 `.barry_workflow/<sid>/cache_refresh.json` `{last_total: 0}` + 一份伪造 jsonl 最后一行 `input_tokens: 250000` → 跑 hook → stdout 应含 BANNER + `cache_refresh.json` 更新。
- 第二次跑（last_total 已更新到 250000，current 还是 250000）→ stdout 无 BANNER。
- 集成测试：本地 v2 仓库正常对话至累计 200k+，下一轮看是否 banner 出现。

**成功标准**：阈值正确触发；不重复触发；hook 失败时不卡 Claude Code（hook 永远 `exit 0`，所有错误吞掉 stderr）；banner 文本同时含 A（cache_hit）+ B（ledger 合规）两段；模型回应里能看到 `[CACHE_REFRESH_DONE 检查项 A+B]` 标记。

## 6. 自反思 round 2

**自检方法**：假设用户读完计划，问"你做的是不是和我说的一样"，找最可能的歧义点。

**可能歧义 #1**：F3 是 **UserPromptSubmit 时一次性 banner**，不是"常驻提醒"。用户 R1 原文 "常驻的也要问题 xxx 文件是否全都在 cache 里面"——"常驻" 可解读为"每轮都问"。但 R2 用户自己给出"每 200k 一次"的工程化方案，等于自我修正了 R1 的"常驻"诉求。
- **决定**：以 R2 为准（用户自己后说），不实现每轮常驻问题。若用户读完计划要求"每轮都问"——回到 router_*.md 加一行而已，成本低。**在 §1 F3 顶部留 explicit note 说明此降级**。← 已加在 §0 锚点引用顺序中（R1→R2→R3 时间序），但 F3 章节本身没明写。**round-2 修补**：F3 章节开头加一行"按 R2 用户提出的 200k 阈值方案，不是 R1 字面的每轮常驻"。

**可能歧义 #2**：F1 viewer 刷新——用户没指定 polling 间隔。我选 5 秒。
- 5 秒 vs 1 秒 vs 30 秒：5 秒是 dev tool 常见值，对 http.server 压力可忽略。用户读完若嫌慢/嫌快很容易调。**接受 5 秒默认，文档化。**

**可能歧义 #3**：F1 "数据源 live 化"用 symlink——如果用户机器 viewer/data/ 之前是 copy 进来的真文件，本次升级会 stale。
- **修补**：F1 升级路径要包含"`rm -rf viewer/data/*/state.md viewer/data/*/action.md` 后让 start_viewer.sh 重新 ingest"，写到测试步骤里。**round-2 加入 §F1 测试段**。

**round 2 输出的修改**：

1. F3 顶部加"按 R2 200k 阈值"声明
2. F1 测试段加"先清旧 state/action 文件再重 ingest"步骤

这两条已记在本 round 2 节末，**不改 §1 正文以保留两轮对比痕迹**——下一轮 commit 时把两条 fold 进 §1。
